RESUMO

O presente trabalho apresenta a especificação técnica, a arquitetura e os resultados práticos da validação de uma plataforma de monitoramento e observabilidade voltada à inspeção contínua de hardware e rastreamento de desempenho de aplicações (APM – Application Performance Monitoring). A indisponibilidade de sistemas e o diagnóstico tardio de sobrecargas de hardware motivaram o desenvolvimento de uma arquitetura híbrida e distribuída. O sistema combina coletores locais baseados no padrão Prometheus Node Exporter, WMI (Windows Management Instrumentation) e utilitário de leitura direta de aceleradores gráficos com a plataforma em nuvem Sentry APM. Para comprovar a eficácia prática da solução em laboratório, foram realizados ensaios empíricos no computador de desenvolvimento, validando o comportamento sob condições nominais (CPU 10%, RAM 73%, Disco 79%, GPU 37%) e sob sobrecarga crítica (>90% de GPU e RAM). Os testes demonstraram a precisão dos gráficos temporais, a sensibilidade da máquina de estados com trava de resfriamento (cooldown de 45 segundos) e o registro forense das ocorrências no Sentry, cumprindo integralmente os objetivos estabelecidos na proposta inicial.

Palavras-chave: Observabilidade. Telemetria de Hardware. Application Performance Monitoring (APM). Sentry. Auto-Discovery. Projeto Interdisciplinar.

1 INTRODUÇÃO E CONTEXTUALIZAÇÃO

O monitoramento contínuo de infraestrutura e de aplicações é um pilar estratégico na engenharia de software e na administração de ambientes computacionais corporativos. Em sistemas modernos, a degradação de recursos físicos como processamento (CPU), memória principal (RAM) ou aceleração gráfica (GPU) pode interromper serviços críticos e comprometer os acordos de nível de serviço (SLA) antes de uma intervenção manual.

Na primeira etapa desta pesquisa, realizou-se um levantamento comparativo de ferramentas de APM (Application Performance Monitoring). Observou-se que soluções tradicionais como o Datadog impõem altos custos por host monitorado (aproximadamente US$ 46/mês combinando APM e infraestrutura) com cobrança pelo pico mensal (high-water mark). Por outro lado, ferramentas como o Better Stack concentram sua atuação em checagens externas sintéticas (HTTP/Ping), sem realizar a instrumentação profunda do código frontend.

Para atender aos requisitos da disciplina de Projeto Interdisciplinar: Monitoramento de Sistemas da Universidade Tuiuti do Paraná (UTP), desenvolvemos uma plataforma de observabilidade sob medida. O sistema integra telemetria direta de hardware local (sem necessidade de cadastros manuais) a uma aplicação web moderna em React e TypeScript, conectando os eventos críticos à plataforma corporativa Sentry APM.

2 OBJETIVOS DO PROJETO

2.1 Objetivo Geral

Desenvolver, documentar e validar experimentalmente uma plataforma web de observabilidade capaz de realizar a descoberta automática de ativos computacionais locais, inspecionar métricas em tempo real de hardware e integrar-se a uma solução de APM para rastreamento de falhas, métricas de transação e gestão do ciclo de vida de incidentes.

2.2 Objetivos Específicos

Conforme estabelecido na proposta original aprovada no primeiro bimestre, definiram-se quatro objetivos operacionais específicos:

  1. Mapeamento de Requisitos e Arquitetura: Estruturar uma arquitetura desacoplada entre coletores locais de hardware, backend de ingestão e interface analítica em tempo real;
  2. Investigação de Agentes e Telemetria de Hardware: Implementar a extração periódica de contadores do sistema operacional (CPU, RAM, Disco) e de aceleração gráfica (GPU), viabilizando descoberta automática (Auto-Discovery);
  3. Estudo e Integração com APM Corporativo: Conectar a camada de aplicação ao Sentry APM, aproveitando sua capacidade de rastreamento de exceções e anexação de metadados enriquecidos de hardware;
  4. Avaliação de Alertas e Resposta a Incidentes: Desenvolver máquina de estados finita com limiares críticos (>90%), notificações visuais flutuantes e resolução automática (auto-recovery).

3.2 Protocolos e Coletores de Hardware

A camada de ingestão estrutura-se a partir de três mecanismos: Prometheus Node Exporter (padrão aberto na porta 9100 para contadores do SO), WMI/Node.js (leitura direta de tempo de CPU via os.cpus() e memória física via os.totalmem()) e Extração de Telemetria de GPU (consulta periódica ao binário do driver gráfico, convertendo carga percentual, VRAM alocada e temperatura em JSON tipado).

4.2 Decisão Técnica pelo Sentry APM

A decisão pelo Sentry fundamentou-se em três pilares: integração nativa com React/TypeScript, enriquecimento de contexto com tags customizadas de hardware e política transparente de acesso acadêmico sem custos.

4.3 Engenharia de Alertas, Cooldown e Máquina de Estados

Para evitar esgotar a cota da API por rate-limit durante sobrecargas sustentadas (devido à varredura a cada 2000 ms), desenvolvemos uma Máquina de Estados Finita com Trava de Resfriamento (*Cooldown*) de 45 segundos:

FIGURA 2 – Máquina de Estados Finita do Motor de Alertas e Auto-Recovery
ESTADO: ONLINE
Métricas em regime nominal de repouso (CPU, RAM, Disco, GPU <= 90%)
▼ Evento de Saturação: Algum recurso ultrapassa o limiar crítico de 90%
ESTADO: CRITICAL (SOBRECARGA DETECTADA)
Emite Toast Vermelho na UI • Dispara Issue Fatal no Sentry • Inicia Cooldown de 45s
PROTEÇÃO ANTI-SPAM (COOLDOWN)
Se o hardware permanecer acima de 90% dentro da janela de 45 segundos:
• Mantém distintivo vermelho CRITICAL na tela
• Bloqueia novos envios ao Sentry para preservar cotas da API
MECANISMO DE AUTO-RECOVERY
Quando todos os recursos retornam para valores <= 90%:
• Emite aviso visual flutuante (toast) verde de normalização
• Marca incidente como resolvido na Central de Alertas
• Transita automaticamente de volta para ONLINE

4.4 Implementação do Algoritmo de Resfriamento

// Controle de resfriamento e disparo seguro no Sentry (src/services/deviceService.ts)
const CRITICAL_THRESHOLD = 90;
const ALERT_COOLDOWN_MS = 45000;
const recentDispatches = new Map<string, number>();

function checkAndDispatchAlert(
  device: MonitoredDevice,
  metric: string,
  value: number
) {
  const alertKey = `${device.id}_${metric}`;
  const now = Date.now();
  const lastTime = recentDispatches.get(alertKey) || 0;

  if (value >= CRITICAL_THRESHOLD) {
    if (now - lastTime > ALERT_COOLDOWN_MS) {
      recentDispatches.set(alertKey, now);

      toast.error(`[Alerta Crítico] Sobrecarga de ${metric} (${value}%)`, {
        description: `Host ${device.name} ultrapassou o limiar de 90%.`
      });

      Sentry.withScope((scope) => {
        scope.setLevel('fatal');
        scope.setTag('resource', metric);
        scope.setTag('hostname', device.name);
        scope.setContext('hardware', { utilization: value, threshold: CRITICAL_THRESHOLD });
        Sentry.captureMessage(
          `[WatchFlow Alert] Sobrecarga Crítica de ${metric} (${value}%)`
        );
      });
    }
  }
}

6.2 Trabalhos Futuros e Conclusão

Como propostas de expansão para etapas futuras, destacam-se a distribuição de coletores empacotados em contêineres Docker para monitoramento de múltiplos servidores em rede acadêmica e o acionamento de rotinas automáticas de remediação (*self-healing*) via webhooks do Sentry.
